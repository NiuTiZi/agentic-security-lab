# 学习与贡献说明

## 本人背景

信息安全方向：安全运营、解决方案与咨询、项目管理与交付。参与过零信任、等级保护类方案
的设计与编写。接触本项目之前：没有 AI Agent 开发经验，没有生产代码开发经验。

## 为什么做这个项目

岗位要求是 Agent 身份与信任安全的产品方案能力。我的判断是：这类岗位最难的部分不是罗列
协议和漏洞名词，而是回答"模型输出不可信时，**谁在哪个位置说了算**"。这个判断来自零信任
方案工作的迁移——把"不信任任何默认身份、每次访问都验证"的思想放到 Agent 场景，
关键差异在于多了一个完全不守规矩的组件（模型）和一个新的信任凭据（任务授权）。

要做能力证据，就不能只画架构图。所以本项目从第一天就定下验收口径：每个控制都必须能
复现风险、能切换配置对照、能重复验收、能出报告。

## 我的贡献（本人完成的部分）

1. **需求与验收设计**：完整需求稿——六类风险目录映射到可执行实验（RISK-01~06）、
   身份与授权用例集（AUTH-01~14、CRED-01~04）、两种实验模式的结论边界（固定回放证明
   服务端控制有效，不证明真实模型会攻击）、诚实统计口径（未复现不包装为防护成功、
   API 失败不静默切换、判定不采信模型自述）
2. **关键安全设计决策**（开发中逐条评审并拍板）：
   - 权限两维度：OAuth scope（应用能做什么）+ 任务授权（此刻替谁做哪件事），模型建议
     不能转化为授权
   - 撤销即时性：组件验证发现"停用客户端后旧令牌验签仍通过"后，坚持增加应用侧在线核验
     兜底（无缓存、下一次调用生效）
   - 错误码分层与根因不掩盖：核验顺序经过返工调整（任务撤销必须先于凭据状态检查，
     否则根因被掩盖；委托范围校验收归后台权威，运行层不重复判断）
   - 出站控制独立于模型行为：唯一出站点 + 按任务隔离的占位符映射 + 实际请求体证据留存
3. **验收与实验分析**：三个阶段验收全部通过后亲自复核报告；真实模型批次 80 次运行中，
   识别出 RISK-04 的"部分效应"（6/10 模型被诱导取资料但拒绝外发）并决定如实标注
   "未复现外发"而非包装成功——这是本项目我认为最有面试价值的一处判断
4. **方案与投递材料**：方案文档（信任边界/接入位置/责任边界/业务影响）、身份与授权报告、
   演示步骤与视频脚本，全部基于本人可复述、可操作、可验证的内容

## AI 辅助开发（如实说明）

代码实现由 AI 编程工具（TRAE）辅助完成：四服务骨架、Keycloak 初始化脚本、LLM 工具调用
循环、验收脚本、前端 UI。本人不具备独立编写这些代码的能力，不以"亲手写了全部代码"
表述本项目。

分工边界：AI 负责把已确认的设计落成代码；本人负责需求定义、设计决策、每一步的验收标准、
运行结果判读与返工方向。举例：AUTH-09 曾出现"撤销任务返回凭据无效而非任务已撤销"，
是我对照错误码分层设计发现根因被掩盖，要求调整核验顺序后修复；阶段2 委托路由破坏了
阶段1 的 AUTH-12，也是回归验收发现后修复——这类设计一致性问题是本人在把控。
