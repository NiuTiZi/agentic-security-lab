# 一页项目介绍：企业客服 Agent 身份与信任安全验证靶场

## 解决什么问题

企业引入大模型 Agent 后，**模型输出不可再当作可信指令**：模型可能被提示注入诱导外发客户资料、
提出越权工具调用；Agent 的 Bearer 令牌可能被窃取；"模型说自己是客服 A"不能成为授权依据。
安全团队需要的不是概念图，而是**能亲手运行、复现风险、验证防护**的证据。

本项目构建了一个可独立运行的验证靶场：真实 OAuth 授权服务（Keycloak）+ 真实大模型
（DeepSeek 工具调用）驱动的客服/退款双 Agent 业务，把 Agent 身份与信任问题变成
可测量、可验收的工程事实。

## 实际完成范围（全部有运行记录）

| 能力 | 实现 | 验收 |

## 主要证据（80 次真实模型运行，0 次 API 错误）

- **数据外发（RISK-01）**：风险配置 10/10 复现——订单中虚构手机号原文进入模型平台请求
  （出站证据可核查）；防护配置 10/10 阻断——出站适配层在请求发出前替换为占位符，0 次泄露，
  用户可见回复按权限还原
- **越权访问（RISK-03）**：风险配置 10/10 复现——他人订单与手机号被返回；防护配置 10/10
  阻断——工具服务对象归属检查（object_ownership）拒绝，模型行为不影响结果
- **间接注入（RISK-04）**：外发未复现（如实标注，deepseek-flash 拒绝执行最后外发步骤）；
  但 6/10 次模型被售后文档中的注入指令诱导提出任务外订单查询并**成功获取客户资料**——
  证明"模型稳健性不可依赖"；恢复服务端任务范围检查后同类提议 100% 被拦截
- **正常业务可用性**：防护全开下合法查询/发送 10/10 完成，投递正文自动脱敏，无误拦截
- **成本与性能**：单次对话平均 3.5~5.9 秒；80 次运行合计约 19.4 万 token（deepseek-flash，temperature=0）

## 对应岗位能力

- **安全方案**：信任边界划分（用户会话/Agent 客户端/工具服务/任务授权/模型平台五方）、
  责任边界（客户数据分类、产品任务确认、业务系统对象归属）、防护失效模式分析
  （如：停用客户端后旧令牌验签仍通过 → 应用侧在线核验兜底）
- **产品落地**：从风险目录到可演示、可验收、可重复的最小闭环；防护开关支持风险复现/单项
  对照/组合防护三态实验；量化验收口径（复现/未复现/部分效应分开表述）
- **工程实现**：四服务独立进程 + 真实 OAuth 组件接入（非自制 JWT 按钮），错误码分层设计，
  全链路审计与出站证据留存

## 主要局限

RISK-02/05/06（跨部门串话、存储运维泄露、委托上下文最小化）为第二阶段范围未实现；
本地回环 HTTP 演示（传输保护未完成）；OIDC 用户登录未实现；提示过滤与脱敏仅覆盖虚构
标记字段，不宣称防住所有变体；模型实验结论仅代表本次样例与运行范围。
